## Context

[Chase Travel](https://www.chase.com/travel) is JP Morgan Chase's travel platform, where Chase cardmembers book flights, hotels, car rentals, cruises and activities with Ultimate Rewards points. I joined its promotions and purchase flow team in January 2025, and I'm the lead developer for the promotions and offers platform, where I own the front-end architecture.

Promotions appear on many squads' pages, so the way squads shared code and releases shaped everything we shipped. Two problems came from the same root, several teams working in one front end:

- **Releases had to be lined up.** Squads shipping into the same front end coordinated their releases with each other, and that coordination became a bottleneck.
- **The same UI was built several times.** Each squad rendered promotions in its own way.

## How I approached it

Both problems are about ownership: who owns a release, and who owns a piece of UI. I made one structural change for each.

## How Module Federation changes the release model

In a single front end, every squad's code is built and released together, so one squad's timing holds up the others. Module Federation, a feature of Webpack, lets separately built applications load each other's code at run time. Each squad's micro-app becomes its own build with its own deployment, and the page brings them together in the browser.

That moves integration from build time to run time. Two things follow from it, and both shaped the design:

- **Shared dependencies need deliberate versions.** Angular and the promotion library are used by every micro-app, so they have to be versioned and shared on purpose, not bundled differently by each squad. That is why Angular upgrades are coordinated across squads.
- **Dependencies between squads still set an order.** Independent deployment doesn't remove dependencies. When one component depends on another, the one it depends on is released first.

<Callout kind="tradeoff">
Independent deployment isn't free. It replaces "release together" with "agree on what's shared", and a shared component library becomes a product with consumers: every change needs versioning and backward compatibility for each squad that builds on it.
</Callout>

## Results

- **Independent teams:** four squads deploy independently instead of lining up every release across teams.
- **Less duplicated work:** three downstream squads render promotions with one shared library instead of building their own.
- **One product:** customers still get one Chase Travel, however many squads build it.
