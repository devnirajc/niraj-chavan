    - title: Sign in
      nodes: [login, session, interceptor, gateway, auth, users]
      detail: The sign-in screen posts credentials; the auth service checks them against the user store and returns an access token and a refresh token. The session service keeps the access token in memory only.
    - title: Every API call
      nodes: [session, interceptor, gateway, apis]
      detail: The interceptor attaches the current access token. Domain APIs validate the signature and claims locally, so there is no extra round trip per request.
    - title: Token expires mid-session
      nodes: [interceptor, gateway, auth, users]
      detail: A 401 makes the interceptor pause the queue and run exactly one refresh, even if ten requests failed at once. The new token replays the queued calls; a revoked refresh token signs the user out instead.

      nodes: [session, guards]
      detail: Guards subscribe to the session state and wait for it to resolve before deciding, so a page refresh never flashes protected content or bounces a signed-in user to the sign-in screen.
decisions:
  - title: Where the access token lives in the browser
    context: >-
      ASSUMED — confirm. Tokens in localStorage survive reloads but are readable
      by any script that runs on the page; an XSS bug becomes account takeover.
    options:
      - name: Memory, with refresh on reload
        chosen: true
        reason: Not reachable from injected script; a reload costs one silent refresh call.
      - name: localStorage
        chosen: false
        reason: Simplest, but exposes the token to any XSS.
      - name: HttpOnly cookie for the access token
        chosen: false
        reason: Safest from XSS but needed CSRF protection and changes to every API.
    tradeoff: One extra request on every full page load, in exchange for tokens that injected script cannot read.
  - title: How concurrent 401s are handled
    context: >-
      ASSUMED — confirm. A dashboard firing ten requests at expiry would
      otherwise trigger ten refreshes, and rotating refresh tokens would
      invalidate each other.
    options:
      - name: Single-flight refresh in the interceptor
        chosen: true
        reason: One refresh, a queue of paused requests, then a replay — invisible to feature code.
      - name: Refresh in each service on failure
        chosen: false
        reason: Duplicated logic and racing refreshes.
    tradeoff: The interceptor became the most delicate code in the app and needed thorough tests for ordering and failure paths.
