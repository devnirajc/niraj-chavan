  Scope Retail's new order management system was an Angular single-page app

    - id: login
      label: Sign-in screen
      layer: client
      detail: Sends the user's sign-in to the backend's token endpoint and keeps the JWT it gets back.
    - id: storage
      label: Token in localStorage
      layer: client
      detail: Keeps the JWT across reloads. Any script on the page can read it, so the page is protected against injected script (Angular's sanitising, HTTPS only, a Content Security Policy) and the server can revoke tokens.
    - id: timer
      label: Renewal timer
      sublabel: before expiry
      layer: client
      detail: Tokens are short-lived, lasting minutes rather than hours. The timer renews each one shortly before it expires, so a signed-in user is not sent back to the sign-in screen partway through a shift.
    - id: interceptor
      label: HTTP interceptor
      sublabel: adds JWT · retries on 401
      layer: client
      detail: One place that adds the token to every API call, so no screen handles tokens itself. If a call comes back 401 because the token has expired, it starts one renewal and retries the call. Other calls that fail meanwhile wait for the same renewal instead of starting their own, then retry once with the new token. The user sees the sign-in screen only if renewal fails.
    - id: guards
      label: Role-based route guards
      layer: client
      detail: Decide which screens each user can open, based on their role. The APIs check the role again, so hiding a screen is never the only protection.
    - id: tokens
      label: Token endpoints
      sublabel: issue · renew
      layer: server
      detail: Added to the existing backend. Issue the JWT at sign-in and renew it before it expires.
    - id: apis
      label: REST APIs
      sublabel: token and role checks
      layer: server
      detail: Check the token and the user's role on every request, and refuse a token that has been revoked.
    - id: revoke
      label: Revocation
      sublabel: sign-out everywhere
      layer: server
      detail: The server keeps a list of revoked tokens and checks it on every request, removing each entry once that token would have expired anyway, so the list stays small. Signing out, or revoking a token, ends access everywhere the user is signed in, before the token would have expired.

decisions:
  - title: How the app proves who is calling the APIs
    context: >-
      The APIs lived on a separate domain from the Angular app, and the
      existing backend's server-session cookies didn't work cleanly between
      them.
    options:
      - name: A JWT sent with every API call
        chosen: true
        reason: Works across the domain split, and every API checks the token and the user's role on each request.
      - name: Server sessions (the existing approach)
        chosen: false
        reason: Their cookies didn't work cleanly between the app and the separate API domain.
      - name: Move the APIs onto the app's domain
        chosen: false
        reason: Not possible. The APIs' domain was fixed, so sign-in had to work across the two domains.
    tradeoff: >-
      The token now lived in the browser, so theft had to be designed for:
      keep injected script off the page, and let the server revoke a token
      early.
  - title: Where the browser keeps the token
    context: >-
      The token had to reach APIs on another domain on every call, and
      survive a page reload.
    options:
      - name: localStorage, sent in a header by the interceptor
        chosen: true
        reason: The simpler option for APIs on another domain.
      - name: An HttpOnly cookie
        chosen: false
        reason: Page script can't read it, but for APIs on another domain it was the less simple option.
    tradeoff: >-
      Any script on the page can read localStorage, so theft was covered
      another way: Angular's built-in sanitising without bypassing it, HTTPS
      only, a Content Security Policy, and a server-side list of revoked
      tokens.
lessons:
  - >-
    Today I'd use a standard identity provider with OpenID Connect instead of
    custom token endpoints, and leave issuing, renewing and revoking tokens to
    a service built for that job.
  - >-
    Concurrent requests are the hard part of token renewal. When several
    calls fail with 401 at once, each will try to renew unless one shared
    renewal is designed in from the start.
  - >-
    Design revocation on day one. A token the server can't take back is a
    security gap that only shows up at the moment you need to close it.

## Context

At Xpanxion (now UST Global) I designed and built the full UI of Scope Retail's order management system, a greenfield Angular application for orders, inventory, the product catalogue, users and reporting. I also designed and built its sign-in and session management end to end: the Angular side, and the token endpoints in the existing backend.

## How I approached it

<Steps
  label="Approach"
  steps={[
    { title: 'Stop relying on cookies', detail: 'Server-session cookies didn\'t work cleanly across the separate API domain, so every API call carries a JWT instead.' },
    { title: 'Renew before expiry, and recover after it', detail: 'A timer renews the token shortly before it runs out. If calls still come back 401, they share one renewal and retry once, so nobody is signed out partway through a shift.' },
    { title: 'Check on the server, not only in the browser', detail: 'Route guards decide which screens a role can open, and every API checks the token and the role again. The server can revoke a token early.' },
    { title: 'Keep injected script off the page', detail: 'The token sits in localStorage, so the app relies on Angular\'s built-in sanitising without bypassing it, and is served only over HTTPS with a Content Security Policy.' },
  ]}
/>

<Callout kind="tradeoff">
A JWT in localStorage survives a reload, but any script that runs on the page can read it. So the protection rests on keeping script off the page and on the server being able to revoke a stolen token. Today I'd hand issuing, renewing and revoking tokens to an identity provider.
</Callout>

## Results

- Operations staff stayed signed in through a working shift, with no surprise sign-outs.
- The design passed security review.
- Sign-in and role checks lived in one place, so new screens reused them instead of writing their own.
- Fewer sign-in and access issues were reported.
