Site Manager (Travel Settings Customisation) is the centralised configuration platform behind [Chase Travel](https://www.chase.com/travel), JP Morgan Chase's travel-booking platform for Chase cardmembers. Authorised business users manage Chase Travel's travel product settings through it, without engineering intervention.

I led the design and implementation of Site Manager. Business teams now manage travel product configuration themselves, through a secure, role-based administration experience. Configuration changes that used to wait days for an engineer and a release now take effect as soon as they are saved. The platform also brought access governance through role-based access control (RBAC) I designed and implemented, enforced by the APIs as well as the Angular layer, and made the dashboard load and respond faster after an observability-led optimisation.

Site Manager is internal, so there is no public demo.

- **Product:** Site Manager, the travel-settings platform for Chase Travel
- **Organisation:** JP Morgan Chase & Co.
- **Users:** authorised business users across Chase Travel's business units, including product, operations and support teams
- **My role:** I led the development of the Angular administration platform, designed and implemented its role-based access control, and drove its performance audit
- **When:** on the Site Manager team from December 2021 to December 2024; since January 2025 I've been on Chase Travel's promotions and purchase flow team

## The business problem

Before Site Manager, changing the configuration of Chase Travel's travel products was engineering work:

- **Every change needed an engineer.** Even simple settings updates went through engineering.
- **Business teams waited on release cycles**, so a configuration change could take days.
- **Access was coarse.** Access management lacked fine-grained controls per business unit.
- **The overhead grew with the product.** As Chase Travel's products became more complex, the operational cost of configuration rose with them.
- **Everyone queued behind the same bottleneck.** Product, operations and support teams all depended on engineers to change settings.

That made it a scaling problem, not just an inconvenience. As Chase Travel's products grew more complex, so did their configuration, and every change still had to go through engineering and a release. The demand on engineers grew with the product, whether or not the work needed an engineer.

## Architecture and design

Site Manager is an Angular administration platform:

- **Reusable component architecture.** I established a component architecture the platform's screens are built from.
- **Configuration-driven UI.** Extensible, configuration-driven UI patterns, so the platform can grow with the settings it manages.
- **Modular features.** Features are designed as modules, which keeps the platform maintainable as it grows.
- **Access control at both layers.** Role-based access control scopes every user's permissions to their business unit and restricts sensitive operations. The Angular layer shows each role only what it may change, and the APIs enforce the same entitlements.
- **Live configuration.** A change made through Site Manager takes effect immediately, not through a release.
- **Micro-app registry.** Chase Travel's micro-apps are registered in Site Manager, so each one can be loaded independently at run time. I worked on the registry feature.

## Performance optimisation

**Problem.** As the settings platform grew, some dashboard pages rendered slowly and responded sluggishly to users.

**Investigation.** I drove a performance audit using application monitoring, log analysis and browser performance profiling.

**Findings.** The audit found three rendering bottlenecks on the dashboard. All three came from rendering work the screens didn't need: components re-rendering when nothing they displayed had changed, and more rendering cycles than the UI required. Separately, the audit showed inefficient patterns in how API calls were made, which added load on top.

**Solution.** Rendering and change-detection fixes for the three bottlenecks, plus lazy-loading improvements and leaner API calls.

**Result.** All three rendering bottlenecks were fixed, and the settings dashboard loads and responds noticeably faster for the business users who configure Chase Travel.

### The three bottlenecks

I found them with Chrome DevTools performance profiles and the Angular DevTools profiler.

**1. The settings list rebuilt every row.** *Cause:* the list's `*ngFor` had no `trackBy`. So whenever a new array arrived from the API, even with unchanged settings, Angular tore down and rebuilt every row. *Fix:* I added `trackBy` on the setting's ID, so Angular reuses the rows it already has and only updates the ones that changed.

**2. Default change detection across the dashboard.** *Cause:* the dashboard's components used the default change-detection strategy. So every async event checked every component, including the ones whose inputs hadn't changed. *Fix:* I moved the presentational components to `OnPush`, with immutable inputs and the `async` pipe, so a component is checked only when its inputs or its own observables change.

**3. Expensive work in templates.** *Cause:* templates called formatting and filtering methods that re-ran on every change-detection cycle. *Fix:* I replaced them with pure pipes and with view models computed once in RxJS streams, so that work runs only when the data changes.

### Why the fixes make the dashboard faster

Before the dashboard can show anything, its code has to load and Angular has to start, its data has to arrive from the APIs, and Angular has to render that data. Each fix targets one of those stages:

- **Lazy loading** means less code has to load before the dashboard can start.
- **Leaner API calls** shorten the wait for the data the dashboard needs.
- **The rendering fixes** cut the work Angular does each time it renders. They help a little on first load, but most of all on every interaction after it: filtering, editing and saving settings.

Of the three, lazy loading made the biggest difference.

## Security and governance

- **Least privilege.** Permissions are scoped per business unit, so a business user can change only the settings that belong to their business unit.
- **Sensitive operations restricted.** Operations that carry more risk require the matching entitlement.
- **Fine-grained entitlements.** Access is managed per role and per business unit, not all-or-nothing.
- **Enforced on the server.** The APIs enforce the same entitlements the Angular layer shows, so a request sent directly to an API by a user without the right entitlement is still refused.
- **Centralised governance.** One platform and one access model for configuration, with audit-friendly administration workflows.

## Business impact

- **Operational efficiency:** settings changes that used to take days now take effect immediately, and routine configuration updates no longer need engineering involvement.
- **Security and governance:** configuration ownership controlled per business unit, with access enforced by the APIs as well as the screens.
- **Performance:** a faster settings dashboard, in loading and in use, for the business users who rely on it.

## Leadership and ownership

I led the development of Site Manager's Angular administration platform and set its architecture: reusable components, configuration-driven UI patterns and modular features. I designed and implemented the role-based access control that governs it, with the same entitlements enforced in the Angular layer and by the APIs. When the dashboard slowed as the platform grew, I drove the performance audit and fixed the bottlenecks. I also worked on its micro-app registry, so each of Chase Travel's micro-apps can be loaded independently.

## Lessons learned

- **Plan lazy loading from the first screen.** Lazy loading made the biggest difference to how fast the dashboard loads. It's easiest to get right when the feature modules are split up at the start, not added once the platform has grown.
- **Make the fast patterns the default.** `OnPush`, `trackBy` and no method calls in templates, enforced through code review or lint rules, so a slowdown can't build up quietly as settings are added. Performance budgets in CI stop it creeping back.
- **Design access control alongside the first screens.** Once business users change settings themselves, role-based access is the main safeguard. I'd define roles and business-unit scopes as early as the screens, and test them as thoroughly as any feature.

## Outcome summary

Site Manager moved routine configuration of Chase Travel's travel products from engineers to the business teams that own it. Because that took changes out of the release process, access control and audit-friendly workflows became the platform's main safeguards, in place of code review and release approval.
