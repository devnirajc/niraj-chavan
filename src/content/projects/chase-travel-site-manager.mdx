Site Manager (Travel Settings Customisation) is the centralised configuration platform behind [Chase Travel](https://www.chase.com/travel), JP Morgan Chase's travel-booking platform for Chase cardmembers. Authorised business users manage Chase Travel's travel product settings through it, without engineering intervention.

I led the design and implementation of Site Manager. Business teams now manage travel product configuration themselves, through a secure, role-based administration experience. Configuration changes that used to wait days for an engineer and a release now take effect as soon as they are saved. The platform also brought access governance through role-based access control (RBAC) I designed and implemented, enforced by the APIs as well as the Angular layer, and improved the dashboard's Largest Contentful Paint by 40% after an observability-led optimisation using Dynatrace and Kibana.

Site Manager is internal, so there is no public demo; the image above is an illustration, not a screenshot.

## The business problem

Before Site Manager, changing the configuration of Chase Travel's travel products was engineering work:

- **Every change needed an engineer.** Even simple settings updates went through engineering.
- **Business teams waited on release cycles**, so a configuration change could take days.
- **Access was coarse.** Access management lacked fine-grained controls per business unit.
- **The overhead grew with the product.** As Chase Travel's products became more complex, the operational cost of configuration rose with them.
- **Everyone queued behind the same bottleneck.** Product, operations and support teams all depended on engineers to change settings.

That made it a scaling problem, not just an inconvenience. As Chase Travel's products grew more complex, so did their configuration, and every change still had to go through engineering and a release. The demand on engineers grew with the product, whether or not the work needed an engineer.

## Architecture and design

Site Manager is an Angular administration platform:

- **Reusable component architecture.** I established a component architecture the platform's screens are built from.
- **Configuration-driven UI.** Extensible, configuration-driven UI patterns, so the platform can grow with the settings it manages.
- **Modular features.** Features are designed as modules, which keeps the platform maintainable as it grows.
- **Access control at both layers.** Role-based access control scopes every user's permissions to their business unit and restricts sensitive operations. The Angular layer shows each role only what it may change, and the APIs enforce the same entitlements.
- **Live configuration.** A change made through Site Manager takes effect immediately, not through a release.

## Performance optimisation

**Problem.** As the settings platform grew, some dashboard pages rendered slowly and responded sluggishly to users.

**Investigation.** I drove a performance audit using Dynatrace, Kibana, browser performance profiling and application monitoring metrics.

**Findings.** The audit found three rendering bottlenecks on the dashboard. All three came from rendering work the screens didn't need: components re-rendering when nothing they displayed had changed, and more rendering cycles than the UI required. Separately, the audit showed inefficient patterns in how API calls were made, which added load on top.

**Solution.** Rendering and change-detection fixes for the three bottlenecks, plus lazy-loading improvements and leaner API calls.

**Result.** All three rendering bottlenecks were fixed. Largest Contentful Paint on the settings dashboard improved by about 40%, and the dashboard responds noticeably faster for the business users who configure Chase Travel.

## Security and governance

- **Least privilege.** Permissions are scoped per business unit, so a business user can change only the settings that belong to their business unit.
- **Sensitive operations restricted.** Operations that carry more risk require the matching entitlement.
- **Fine-grained entitlements.** Access is managed per role and per business unit, not all-or-nothing.
- **Enforced on the server.** The APIs enforce the same entitlements the Angular layer shows, so a request sent directly to an API by a user without the right entitlement is still refused.
- **Centralised governance.** One platform and one access model for configuration, with audit-friendly administration workflows.
- **Outcome.** Zero privilege-escalation incidents since launch.
