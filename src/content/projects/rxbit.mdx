Rxbit is a prescription builder for small clinics. The doctor keeps one record per patient, with allergies and existing conditions flagged where they cannot be missed, and writes each visit as a structured prescription: the complaint, the diagnosis, each medicine with its dosage and duration, and the advice to go home with. Any visit can be previewed, printed or saved as a PDF, and the whole history stays on the patient's page.

It is my own side project, which I designed and built.

- **Who it's for:** doctors running small clinics, writing prescriptions during a consultation
- **What it saves:** retyping common prescriptions. Repeat cases start from a saved protocol, and medicines come from the clinic's own drug library
- **Shape:** an installable web app that keeps its data on the clinic's own device
- **My role:** designer and engineer: product, UX, front end, storage and deployment

## The business problem

A prescription is written under time pressure, with a patient in the room, and mistakes matter. A small clinic's doctor needs to:

- see allergies and existing conditions before choosing a medicine,
- write the same kinds of prescription for common cases without retyping them,
- hand the patient a clear, printed prescription on the clinic's own letterhead,
- keep each patient's visit history and follow-up dates in one place.

Rxbit is built around those four needs.

## Architecture and design

Rxbit is a React single-page application built with Vite, and it is **local-first**: patient records, visits, the drug library and protocol templates live in the browser's IndexedDB, through Dexie, on the clinic's own device. The app is explicit about this. Saved protocols are labelled "saved on this device only", and the backup screen offers to "export a copy of everything on this device" as a JSON file that can be restored later.

State lives in Zustand stores, and storage sits behind one interface with two implementations: Dexie over IndexedDB in the browser, and SQLite when the same codebase is packaged for Android and iOS with Capacitor. The codebase also packages as a desktop app with Electron. A web app manifest and service worker make the web version installable, with an offline mode.

Heavy code loads only when it is needed. The PDF engine (pdfmake, with its embedded fonts) is a separate chunk fetched on the first print or export, and the starter drug list is a separate chunk loaded only on first run or when a newer version of the list ships.

## Key technical challenges

### Prescriptions that print like the real thing

**Challenge.** A prescription is a physical document the patient takes to a pharmacy. It has to carry the clinic's identity and read clearly on paper.

**Solution.** A clinic profile with letterhead and header templates drives every printed prescription and PDF, and Rxbit won't print or export until the profile is set up. The drug table's layout is configurable, including a compact style with less row spacing and an optional drug-type column. Diagnosis codes can be printed alongside the diagnosis. The layout is print-optimised for physical prescriptions.

PDFs are generated in the browser with pdfmake, so printing and exporting need no server. A prescription can be printed, downloaded, shared as a link or printed in three copies, with five letterhead templates to choose from and a live preview of exactly what will print.

### Speed in the consultation room

**Challenge.** The doctor writes while the patient waits, so typing the same prescription for common cases is wasted time.

**Solution.** Protocol templates: any visit can be saved as a template and loaded into a new visit, and Rxbit ships with starter protocols such as hypertension follow-up, acute pharyngitis, paediatric fever and antenatal routine. Medicines from a patient's previous visit can be carried over, drug search draws on the clinic's own library, and keyboard shortcuts come with an in-app list of the shortcuts each view supports.

### Patient data that stays on the device

**Challenge.** Patient records are sensitive, and a hosted database means someone has to run and secure a server and hold the clinic's data.

**Solution.** Records stay in IndexedDB on the clinic's own device, and the doctor controls backups: one JSON file holds everything and restores it.

The trade-off is that the device holds the only copy. Nothing syncs between devices, so a backup is the doctor's responsibility, and restoring a backup replaces everything currently on the device.

### Warnings that help without pretending to be a clinical database

**Challenge.** Drug interactions are the riskiest thing a prescription tool can get wrong. A warning that fires too often gets ignored, and one that claims more certainty than it has is dangerous.

**Solution.** As each medicine is added, Rxbit checks it against the patient's recorded allergies, the medicines already on the prescription, and a set of interaction rules that ships with the app. Each rule pairs groups of drug-name keywords, such as warfarin with common NSAIDs, and carries a severity (major or moderate) and a plain-language effect: "Increased bleeding risk — NSAID + warfarin". The rules match on the drug name as entered, so a brand name that doesn't contain the generic name won't trigger them. Coverage is best-effort by design: the warnings support the doctor's judgement, they don't replace it.

## Accessibility

Rxbit is built to WCAG 2.1, with keyboard-navigable forms throughout. The prescription form can be completed without a mouse, and keyboard shortcuts speed up the common actions.

## Security and privacy

Patient records stay on the device in the browser's IndexedDB, and the app says so where it saves templates and backups. Backups are files the doctor exports and keeps, not copies held by a third party.

Restoring a backup checks that the file is an Rxbit backup with a known schema version before touching anything, asks the doctor to confirm, and replaces the data inside one transaction, so a failed restore doesn't leave half the records behind.

## Performance

- **PDF engine on demand.** pdfmake and its fonts load on the first print or export, and are pre-warmed in the background so the first click doesn't wait for the download.
- **Starter data on demand.** The starter drug list is its own chunk, loaded only on first run or when a newer list ships. On every other start, a version check in a tiny module is all that runs.
- **Storage loaded per platform.** The browser build loads only the IndexedDB storage code, and the mobile builds only the SQLite code.

## Outcome summary

- **What it is:** a working, installable prescription builder: patient records, structured prescriptions, protocols, drug-interaction warnings and print-ready output.
- **Technical approach:** local-first storage behind one interface (IndexedDB in the browser, SQLite on mobile), PDF generation loaded on demand, and offline support as an installable app.
- **Quality bar:** keyboard-navigable to WCAG 2.1, with shortcuts for speed and a print layout built for real prescriptions.
