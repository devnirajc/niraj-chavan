Nexpenso turns bank statements into a picture of where the money goes. Upload a statement — CSV, Excel or plain text — and it categorises every transaction, flags duplicates by their reference number, and rolls everything up into dashboards: spending by category, balances per bank, upcoming bills and subscriptions, savings goals and investments.

It is my own side project: a React single-page app with a Node.js and Express API over PostgreSQL. I designed and built it.

- **Who it's for:** people tracking money across accounts at several Indian banks. Duplicates are matched on UTR, UPI reference or cheque number
- **Shape:** a React app on Netlify, calling a REST API on the same origin under `/api`; Netlify proxies `/api` to the API, which runs in Docker on Northflank, and categorisation runs in a separate Python service
- **My role:** designer and engineer: product, front end, API, data model and deployment

## The business problem

Bank statements are the most complete record of where money goes, but a statement is a list of transactions, not an answer. Turning a year of statements from several banks into answers means:

- importing whatever format each bank exports,
- categorising hundreds of transactions without doing it by hand every month,
- not double-counting when statements overlap,
- recognising money moved between your own accounts, so it isn't counted as spending,
- spotting the bills and subscriptions that recur.

Nexpenso does each of these.

## Architecture and design

Nexpenso is a React single-page app with Redux for state and React Router for navigation, built with Vite and charted with Chart.js. Vendor code is split into separate chunks — React, Redux, charting and data handling — which the page preloads in parallel, so changing application code does not invalidate the cached libraries.

All network behaviour lives in **one API client**. Screens call functions such as "create transactions in bulk" or "check for duplicates", and the client deals with tokens, CSRF, timeouts, retries and cold starts. The diagram below shows the moving parts.

The API is organised by resource: transactions and transfers, categories and categorisation rules, bills and their payments, goals, investments, analytics and preferences. One request can load the app's initial data together with its analytics.

Inside, the API follows routes, controllers and services: one Express router per resource, a service layer for the business logic, and SQL through node-postgres on PostgreSQL. Statement imports run as jobs on pg-boss, a job queue that lives in PostgreSQL itself, so there is no separate queue server to run. Netlify proxies `/api` to the API host, which keeps every call same-origin (see the decisions below).

## Key technical challenges

### A server that might be asleep

**Challenge.** The API can be idle when a user arrives, and the app's own error messages allow for it: "the server may be waking up". A cold start looks like a failed request: a timeout, a 502 or 503.

**Solution.** Before signing in, the client sends a liveness probe, up to three attempts with growing delays. The probe is shared by concurrent callers and skipped if one succeeded in the last 30 seconds. Gateway errors and network failures are retried up to three times with growing delays, only while the browser is online. Every failure that gets through becomes a specific, plain-language message: no internet connection, the request timed out, the server is starting up, the browser blocked the connection, or too many attempts with a wait time.

### Importing messy statements without double-counting

**Challenge.** Statements from different banks overlap and arrive in different formats, and importing the same transaction twice corrupts every total built on it.

**Solution.** Nexpenso accepts CSV, XLSX, XLS and TXT against a published column format, and matches duplicates on each transaction's own reference: UTR, UPI reference or cheque number. New transactions are checked for duplicates before they are kept. There is a full rescan of existing data, a way to mark a false positive as not a duplicate, and a backfill that adds references to older transactions. Imports are tracked as background jobs that can be checked and cancelled. Transfers between your own accounts are recorded as linked transactions, with a repair tool for links that break.

The import worker writes in chunks of 250 rows. When the database reports a transient error, it halves the chunk and retries, down to 25 rows, so a busy moment on the database doesn't fail a whole statement. It pauses briefly between write bursts so the app's own reads aren't starved on a small database, and checks duplicates and categorises in chunks of their own. Each job carries an idempotency key, so submitting the same import twice returns the existing job instead of starting a second one.

### Categorisation that improves with use

**Challenge.** Categorising hundreds of transactions by hand every month is slow and tedious.

**Solution.** AI-assisted categorisation, with endpoints for user feedback, retraining and statistics, alongside user-defined rules for future uploads. Rules can be reordered, exported and imported, and categories form a tree whose branches can be merged.

Categorisation runs in two layers:

- **A per-user model.** A separate Python service (FastAPI, on Hugging Face Spaces) trains a model for each user on their own labelled transactions: character and word TF-IDF features from the description, plus amounts and dates, fed to a LightGBM classifier. Each prediction comes with a confidence score and the top three categories. Corrections the user makes are queued as feedback and merged into the training data on the next retrain.
- **A fallback that never goes away.** The API also has its own TypeScript engine with rules, merchant recognition and pattern matching. A circuit breaker in the API's ML client opens after repeated server-side failures, so a cold or failing ML service falls back to that engine quickly instead of making every upload wait. A low-confidence "Uncategorised" or "Others" from the model never overwrites a category the user's own rule has set.

## Security

- **Sessions:** sign-in sets a signed JWT in a cookie that page scripts can't read (HttpOnly), Secure in production, with a seven-day lifetime that matches the token's. Because Netlify proxies `/api`, the cookie is first-party and the browser sends it with every request. The API also accepts the token as a bearer header, which the client keeps in `sessionStorage` as a fallback for browsers that block cookies.
- **CSRF:** every state-changing request (POST, PUT, PATCH, DELETE) outside the sign-in, registration and password-reset endpoints carries a CSRF token. A rejected token is refreshed and the request retried once. A second failure asks the user to refresh.
- **Abuse:** rate-limited responses (HTTP 429) are surfaced with how long to wait.
- **Destructive actions:** deleting an account asks for the password again.
- **Logs:** console output is filtered so passwords, tokens, API keys and card details are redacted, and logged request details show the `Authorization` header as redacted.

On the server, passwords are hashed with bcrypt, and the API reads the session cookie first and the bearer header second. CSRF tokens carry their own expiry. Rate limits use a sliding window in Redis, with an in-memory fallback, and HTTP security headers are set with Helmet.

## Performance

- Vendor code (React, Redux, charts and data handling) is split into long-cached chunks that the page preloads in parallel.
- Initial data and analytics can arrive in one request rather than several.
- Heavy calls get their own timeouts: up to 60 seconds for duplicate scans, 90 seconds for bulk imports and 120 seconds for reference backfills. Everyday requests stay at 30 seconds.

## Automation and monitoring

- **Background imports:** statements are processed as upload jobs the app can track and cancel.
- **Recurring bills:** the API detects bills and subscriptions that recur.
- **Import telemetry:** after an import, the client posts a summary to a telemetry endpoint. The call is fire-and-forget, with a five-second timeout and errors ignored, so instrumentation can never block or break an import.
- **Delivery:** the API runs in a Docker container on Northflank, and the ML service in its own container on Hugging Face Spaces. The API has unit and integration tests in Vitest.

## Outcome summary

- **What it is:** a working personal-finance product, from statement import to dashboards, bills, goals and investments, on a front end and API I built.
- **Engineering depth:** duplicate detection on payment references, idempotent background import jobs on a PostgreSQL-backed queue, and a per-user categorisation model with a rules engine behind it.
- **Production habits in a side project:** CSRF protection, retries with back-off, cold-start handling, redacted logs and fire-and-forget telemetry.
