[Chase Travel](https://www.chase.com/travel) is JP Morgan Chase's travel platform. Chase cardmembers use it to book flights, hotels, car rentals, cruises and activities, earning and redeeming Ultimate Rewards points. Offers are central to the product: Points Boost, for example, makes points worth more when they are spent through Chase Travel. The platform serves millions of customers.

I worked on two parts of Chase Travel that decide whether a customer books.

- **The promotions and offers platform**, which puts offers in front of customers. I'm its lead developer. I delivered personalised offer rendering across the platform, built the shared component library other squads render promotions with, and redrew the boundaries between squads' code so each could deploy on its own.
- **The purchase flow**, the steps where a customer's choices become a booking: trip cart, traveller information, payment and review, and confirmation.

Alongside both, I run design and code reviews for the team.

## The business problem

A booking on Chase Travel depends on two things: the offers that draw a customer in, and a purchase flow that turns their choices into a confirmed trip.

Offers are central to Chase Travel: the public site leads with them, and how well they reach a customer affects whether that customer books. The offers work started from four problems:

- **Personalised offers weren't available across the platform.** Customers needed to see the offers relevant to them, wherever they were in Chase Travel.
- **Promotion UI was duplicated.** Squads rendered promotions in their own ways, so the same work was done several times.
- **Releases needed cross-team coordination.** Squads working in the same front end had to line up their releases, which became a bottleneck.
- **Accessibility needed an audit.** The platform had to meet WCAG 2.1 AA, which meant finding and fixing the gaps across Chase Travel.

## Architecture and design

The promotions work changed Chase Travel's front end in two structural ways:

- **Micro-frontend boundaries.** I introduced module boundaries using Webpack Module Federation, so each squad's part of the front end builds and deploys independently while customers still get one Chase Travel. Each micro-app is registered in Site Manager's registry, which holds its bundle address and its configuration for each client, and a dynamic element loader provided by the core team reads the registry and loads each micro-app at run time. Angular upgrades are coordinated through the common platform with all the squads, so every micro-app stays on one Angular version.
- **A shared promotion-rendering library.** I architected a reusable Angular component library that renders promotions. Three downstream squads build on it rather than maintaining their own.

### Many squads, one product

**Challenge.** Several squads ship into Chase Travel's front end. Shared releases slowed everyone down, and each squad was building its own promotion UI.

**Solution.** Two changes, one per problem: Module Federation boundaries so squads deploy independently, and a shared promotion-rendering library so they stop rebuilding the same components.

**Outcome.** Four squads deploy independently without cross-team release coordination. Three downstream squads render promotions with the shared library instead of building their own.
