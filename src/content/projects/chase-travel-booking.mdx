[Chase Travel](https://www.chase.com/travel) is JP Morgan Chase's travel platform. Chase cardmembers use it to book flights, hotels, car rentals, cruises and activities, earning and redeeming Ultimate Rewards points. Offers are central to the product: Points Boost, for example, makes points worth more when they are spent through Chase Travel.

I worked on two parts of Chase Travel that decide whether a customer books.

- **The promotions and offers platform**, which puts offers in front of customers. I'm its lead developer. I delivered personalised offer rendering across the platform, built the shared component library other squads render promotions with, and redrew the boundaries between squads' code so each could deploy on its own.
- **The purchase flow**, the steps where a customer's choices become a booking: trip cart, traveller information, payment and review, and confirmation.

Alongside both, I run design and code reviews for the team.

## The business problem

A booking on Chase Travel depends on two things: the offers that draw a customer in, and a purchase flow that turns their choices into a confirmed trip.

Offers are central to Chase Travel: the public site leads with them, and how well they reach a customer affects whether that customer books. The offers work had four goals:

- **Personalised offers across the platform.** Show each customer the offers relevant to them, wherever they are in Chase Travel.
- **One way to render promotions.** Squads rendered promotions in their own ways, so the same work was done several times.
- **Independent releases.** Squads working in the same front end had to line up their releases, which became a bottleneck.
- **Accessibility.** Meet accessibility standards (WCAG 2.1 AA) across Chase Travel.

## Architecture and design

The promotions work changed Chase Travel's front end in two structural ways:

- **Micro-frontend boundaries.** I introduced module boundaries using Webpack Module Federation, so each squad's part of the front end builds and deploys independently while customers still get one Chase Travel. Each squad's micro-app is loaded at run time. Release order still matters when one component depends on another: the one it depends on is released first, and the dependent one goes live after it. Angular upgrades are coordinated across the squads, so every micro-app stays on one Angular version.
- **A shared promotion-rendering library.** I architected a reusable Angular component library that renders promotions. Three downstream squads build on it rather than maintaining their own.

## Key technical challenges

### Personalised offers across the platform

**Challenge.** Render offers personalised to each cardmember, wherever they are in Chase Travel.

**Solution.** I delivered personalised offer rendering across Chase Travel.

**Outcome.** Personalised offers now render across the platform.

### Many squads, one product

**Challenge.** Several squads ship into Chase Travel's front end. Shared releases slowed everyone down, and each squad was building its own promotion UI.

**Solution.** Two changes, one per problem: Module Federation boundaries so squads deploy independently, and a shared promotion-rendering library so they stop rebuilding the same components.

**Outcome.** Four squads deploy independently instead of lining up every release across teams. When one component depends on another, the one it depends on still goes out first. Three downstream squads render promotions with the shared library instead of building their own.

### Accessibility across the platform

**Challenge.** Chase Travel had to meet WCAG 2.1 AA.

**Solution.** I led the accessibility compliance audit and remediation across the platform, implementing keyboard navigation, ARIA landmarks and screen-reader support.
