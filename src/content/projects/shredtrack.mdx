ShredTrack tracks what goes into a cut. Each day shows calories, protein, carbs and fat against personal targets, the food logged so far by meal, and a tip based on what is left: "Protein at 69g/210g — add chicken, paneer, or a whey shake." Workouts, progress and goals sit alongside, along with an AI meal planner.

It is my own side project, which I designed and built.

- **Who it's for:** someone on a cut who needs to hit calorie and protein targets every day
- **Shape:** an installable Next.js app on Vercel, with sign-in and storage on the device
- **My role:** designer and engineer

## The business problem

A cut is won or lost on daily numbers: calories under target, protein at target, day after day. A tracker that only records what you ate leaves the question that matters to you: *what should I eat next?*

ShredTrack answers that question. Its tips work from what is left for the day, and the AI meal planner works ahead.

## Architecture and design

ShredTrack is a Next.js application using the App Router, deployed on Vercel, with a web app manifest so it installs to a phone's home screen. Users sign in with an email and password, and the app uses IndexedDB, through Dexie, for storage on the device.

Two halves do different jobs:

- **On the device:** the user's profile, targets, food log, workouts and custom foods live in IndexedDB through Dexie. The food list starts from a seeded set of 35+ foods, Indian staples among them, and grows with the user's own entries.
- **On the server:** Next.js route handlers do the AI work: the meal planner, the workout planner, looking up and correcting foods, and estimating a meal from a photo. They call models on Groq's API, so the API key never reaches the browser. Each request sends a small summary of the day (targets, what has been eaten, recent workouts), and the handler builds the prompt from it.

## Key technical challenges

### AI models that disappear on short notice

**Challenge.** The hosted models behind the AI features can be retired with little warning. ShredTrack has had to swap models twice since launch: the vision model, and later the text model, ahead of its shutdown date.

**Analysis.** A model ID hard-coded in the app turns every retirement into an emergency code change. And reasoning settings differ between model families. Sending the wrong pair is rejected with an error, not ignored, so an override could fail every request at the moment it was needed most.

**Solution.** Model IDs live in one module and can be overridden by environment variables, so the next swap is a configuration change rather than a deploy. Reasoning settings are derived from the model family in use, and an unrecognised model gets a plain request any model will accept.

### Reasoning that cost correctness

**Challenge.** On a realistic five-item food prompt, one model spent 3,986 tokens reasoning, ran out of its 4,096-token budget, and returned JSON that couldn't be parsed.

**Analysis.** Every AI call in the app is recall or formatting: look up a food, fill in its macros, write a short plan. A reasoning pass bought nothing for that work, and cost both speed and correctness.

**Solution.** Reasoning is turned off for those calls. The same prompt then answered correctly in 244 tokens, in 754 ms instead of 8,100 ms. Responses cut off by the token budget are logged, so a truncation shows up instead of passing as a short answer.

### Failures that looked like answers

**Challenge.** The meal planner shows the model's reply as a chat message. If an upstream failure came back as an ordinary response, the app would show an error string as if it were coaching advice.

**Solution.** Upstream failures are returned with error status codes (502, or 503 when the provider is busy), and an empty reply counts as a failure. The client can then show an error as an error. Each route also sets its own time limit, shorter than the client's, so the server's clear message arrives before a generic timeout.

## Security

- **Passwords:** hashed with bcrypt, and only the hash is kept on the device.
- **Sessions:** the server issues a signed session cookie that page scripts can't read (HttpOnly), sent only to the same site and only over HTTPS in production. It expires after seven days, and it is checked on every AI request with a constant-time signature comparison.
- **Abuse:** AI requests are rate-limited per client: ten a minute for text and five for the more expensive photo analysis. Creating a session is limited too, and needs a custom header, so another site can't create one cross-origin.
- **Input:** the day's summary is clamped to sensible ranges and trimmed before it goes into a prompt, and uploaded photos are checked for type and size.
- **Fails closed:** in production, a missing session secret refuses every request instead of skipping the check.

<Callout kind="tradeoff">
The rate limiter keeps its counts in memory, so on serverless hosting each instance counts on its own and the limit is per instance, not global. That's fine for a side project, and the code says so; a shared store such as Redis would make it strict.
</Callout>

## Outcome summary

- **What it is:** a live, installable tracker for calories, macros, meals and workouts, with an AI meal planner.
- **Product focus:** guidance as well as logging, with tips that start from what is left for the day.
- **Technical approach:** Next.js on Vercel, with the user's data on the device and AI calls behind server route handlers that keep the provider key, rate limits and model choices on the server.
